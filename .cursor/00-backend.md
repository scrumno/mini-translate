## Правила реализации бэкенда (Expoline, Bitrix, Slim, DDD) 
 
Этот документ описывает единые правила разработки бэкенда проекта на PHP 8.2 с использованием Bitrix D7, Slim и DDD‑подхода. Все новые реализации должны строго соответствовать этим правилам. 
 
--- 
 
## 1. Общая архитектура и слои 
 
- Версия PHP: 8.2, в каждом файле ставим declare(strict_types=1);. 
- Пространства имён: все классы в пространстве имён Expoline\... (PSR‑4: Expoline\ → `local/classes/Expoline`). 
- Фреймворк HTTP: Slim, точка входа api/v1/index.php, приложение и маршруты настраиваются через DI‑контейнер. 
- DI‑контейнер: PHP‑DI v7, конфигурация через laminas-config-aggregator. 
- Организация конфигов: 
  - Composer‑autoload: в local/composer.json, подключается через bitrix/php_interface/init.php и local/vendor/autoload.php. 
  - Инициализация контейнера: api/v1/config/container.php (`new ContainerBuilder()`, `addDefinitions(require 'dependencies.php')`). 
  - dependencies.php использует ConfigAggregator и подхватывает файлы из api/v1/config/common/*.php. 
  - Файлы конфигурации именуем по домену в kebab‑case (`billing.php`, auto-invoce.php, tenders.php и т.п.). 
 
- DDD‑подход: 
  - Внешний мир (HTTP, Bitrix‑ивенты и пр.) общается с доменом только через: 
    - **Command**‑обработчики (`Handler`), 
    - **Query**‑фетчеры (`Fetcher`), 
    - Listener (обработчики событий Bitrix). 
  - Нельзя использовать классы домена напрямую из HTTP‑слоя или Bitrix‑скриптов, только через перечисленные фасады. 
  - Агрегаты внутри домена опциональны; при прочих равных стараемся обходиться без сложных агрегатов. 
  - Не используем value‑objects без острой необходимости. 
 
--- 
 
## 2. Структура модулей и доменов 
 
- Корневая папка доменов: local/classes/Expoline/{Domain}. 
- Пример домена: local/classes/Expoline/Billing. 
 
- Подпапки домена: 
  - Entity/{Entity}/ — сущности и репозитории: 
    - {Entity}.php — сама сущность. 
    - {Entity}Repository.php — репозиторий. 
    - Дополнительно могут быть таблицы D7 (`{Entity}Table.php`) и типы (`{Entity}Type.php`). 
  - Command/{UseCase}/ — команды: 
    - Command.php — DTO команды. 
    - Handler.php — обработчик use‑case. 
  - Query/{UseCase}/ — запросы: 
    - Query.php (при необходимости) — DTO запроса. 
    - Fetcher.php — фетчер, возвращающий DTO или массивы. 
  - Service/ — доменные сервисы и вспомогательная логика (например, `AutoInvoiceCreator`). 
  - EventRegister/ — файл events.php для регистрации Bitrix‑событий. 
  - Listener/{Logic}/Handler.php — обработчики событий Bitrix. 
 
- HTTP‑слой: 
  - local/classes/Expoline/Http/Action/{Domain}/ — HTTP‑actions. 
  - Класс Action реализует RequestHandlerInterface. 
  - Пример: Expoline\Http\Action\Billing\CreateKeyAction. 
 
--- 
 
## 3. HTTP‑слой (Slim Actions) 
 
- Расположение: local/classes/Expoline/Http/Action/{Domain}/{UseCase}Action.php. 
- Интерфейс: каждый Action реализует Psr\Http\Server\RequestHandlerInterface. 
- Конструктор: 
  - Внедряем зависимости через DI (команды/фетчеры/сервисы). 
  - Свойства конструктора объявляем как private readonly. 
  - Используем именованные параметры при создании DTO/команд. 
 
- Метод `handle`: 
  - Структура: 
    - Парсим запрос через RouteContext::getArgument, getParsedBody(), getQueryParams(), getUploadedFiles() и т.п. 
    - Создаём Command/Query с использованием именованных аргументов. 
    - Вызываем fetcher->fetch(...) или handler->handle(...). 
    - Нормализуем результат к массивам/DTO. 
    - Возвращаем JSON через готовый класс: 
      - return new \Expoline\Http\Response\JsonResponse(['данные'], 200); 
  - Исключения: 
    - В Action допустим один внешний try-catch: 
      - На \InvalidArgumentException возвращаем 400 с описанием ошибки. 
      - На остальные \Throwable — логируем и возвращаем 500/400, по контексту. 
    - Логирование: 
      - \Expoline\Service\Logger::toFile('домен/use-case', ['message' => ..., 'trace' => ...]); 
      - Имена логов в формате домен/use-case, части разделяем дефисом (например, `billing/create-key`). 
  - Где можно использовать `try-catch`:

  - Только в Action и в редких случаях итеративной обработки с фиксацией ошибок без остановки работы. 
    - В репозиториях, сущностях и простых сервисах `try-catch` не использовать.

## 4. Команды (Command) и обработчики (Handler) 
 
- Расположение: local/classes/Expoline/{Domain}/Command/{UseCase}/. 
 
- Command: 
  - Лёгкий DTO‑класс без логики. 
  - Свойства публичные, типизированы, без геттеров/сеттеров (если нет особой необходимости). 
  - Создание только через конструктор с type hints. 
 
- Handler: 
  - Имеет строгий namespace Expoline\{Domain}\Command\{UseCase}. 
  - Конструктор: 
    - Внедряет репозитории и сервисы, необходимые для use‑case. 
    - Свойства объявляются как private readonly, имена свойств репозиториев — во множественном числе по имени сущности, без суффикса Repository (например, $keys для `KeyRepository`). 
  - Метод handle: 
    - Имя метода: handle. 
    - Аргумент: конкретный Command. 
    - Возвращаемый тип: 
      - Если результат обязателен — строгий тип, без null. 
      - Если может отсутствовать — ?Тип или Тип|null. 
    - Возврат DTO или bool|void по задаче. 
    - Бизнес‑логика внутри: 
      - Работа с сущностями и репозиториями. 
      - Вызовы других доменных сервисов/обработчиков. 
    - Никакого Bitrix‑кода в Handler. 
  - Статические фабрики обработчиков: 
    - Если создаётся статический Handler`/`Listener, предварительную обработку параметров делаем в этом же методе только если не нужны дополнительные запросы. 
    - Если нужны дополнительные запросы — выносим ответственность в соответствующую Command/Query, но не передаём внутрь весь event, а извлекаем нужные данные и передаём параметрами. 
 
--- 
 
## 5. Запросы (Query) и фетчеры (Fetcher) 
 
- Расположение: local/classes/Expoline/{Domain}/Query/{UseCase}/. 
 
- Query: 
  - По аналогии с Command, DTO без логики. 
 
- Fetcher: 
  - Namespace Expoline\{Domain}\Query\{UseCase}. 
  - Метод fetch(Query $query): DTO|array. 
  - Возвращает: 
    - DTO, 
    - массив DTO, 
    - массив ассоциативных данных (по задаче). 
  - Фетчер не знает о HTTP/Bitrix; только о домене и репозиториях. 
 
- DI: 
  - Fetcher, Handler, Listener не описываем отдельно в конфигурации DI — они подхватываются автоматически через Slim. 
 
--- 
 
## 6. Сущности (Entity) 
 
- Расположение: local/classes/Expoline/{Domain}/Entity/{Entity}/{Entity}.php. 
 
- Требования к сущности: 
  - Пространство имён: Expoline\{Domain}\Entity\{Entity}. 
  - Свойства: 
    - Публичные, неизменяемые по контракту (не использовать сеттеры без необходимости). 
    - Не объявляем свойства как readonly, но изменение значений вне конструктора логикой не предполагается. 
    - Идентификатор сущности — свойство id в нижнем регистре: public string $id. 
  - Константа BASE_SELECT: 
    - Определяет набор полей для Bitrix‑запросов. 
  - Конструктор: 
    - Все параметры строго типизированы. 
    - id задаётся как string. 
  - Статический конструктор buildNew(...): 
    - Используется при создании новых сущностей. 
    - Не делает проверок обязательных полей, не бросает исключений. 
    - Всегда задаёт id как пустую строку '' (новая сущность). 
  - Статический конструктор buildFromData(array $data): self: 
    - Маппинг из массива (Bitrix‑данные) в сущность. 
    - Без лишних временных переменных и проверок, только необходимое приведение типов и преобразование дат. 
    - Не делает лишних проверок и валидаций, только технические преобразования (например, строка → `Date`). 
  - Метод getData(): array: 
    - Обязан возвращать массив данных в bitrix‑формате на основе свойств сущности и BASE_SELECT. 
    - Не делает проверок на пустоту, просто собирает данные. 
  - Валидация: 
    - Не создаём отдельный метод валидации. 
    - Все проверки свойств (бизнес‑правила) выполняются внутри доменных методов сущности (если они есть), либо в Handler/Service, но не в buildNew и не в buildFromData.

## 7. Репозитории (Repository) 
 
- Расположение: local/classes/Expoline/{Domain}/Entity/{Entity}/{Entity}Repository.php. 
 
- Общие правила:

- Namespace: Expoline\{Domain}\Entity\{Entity}. 
  - Репозиторий отвечает за: 
    - Получение данных из Bitrix (D7 ORM и/или старое ядро — по правилам ниже). 
    - Маппинг данных в сущности через Entity::buildFromData(...). 
    - Генерацию доменных исключений при ошибках. 
 
- Работа с Bitrix: 
  - Для чтения используем Bitrix D7 ORM. 
  - Старое ядро (`CIBlockElement` и т.п.) используем только для добавления элементов инфоблока (create/save). 
  - Не делаем в репозитории проверок на: 
    - подключение модулей (`Loader::includeModule`), 
    - существование iblockId, 
    - наличие entityClass. 
  - Блокировка try-catch: 
    - В репозиториях запрещено использовать try-catch. 
    - Если нужно выбросить ошибку — кидаем исключение напрямую. 
 
- Идентификаторы инфоблоков: 
  - Получаем только через готовый метод: 
    - (new \Expoline\Service\IBlockHelper())->getIBlockIdByCode('iblock_code'); 
  - В common`‑конфиге домена инициализируем репозиторий с `iblockId, полученным этим методом, и передаём внутрь через конструктор. 
 
- Сигнатуры методов: 
  - Если метод обязан вернуть сущность/данные: 
    - Имя начинается с get.... 
    - При отсутствии данных кидаем \DomainException с текстом на русском. 
  - Если метод может не вернуть данные: 
    - Имя начинается с find.... 
    - Возвращаем null при отсутствии (например, ?Entity или `?array`). 
  - Методы, возвращающие коллекции: 
    - Имя может быть findAllBy..., findBy..., getAll... и т.п., в зависимости от контракта. 
    - При необходимости отсутствия элементов: 
      - Возвращаем пустой массив, 
      - Или кидаем \DomainException, если по бизнес‑логике пустой результат — это ошибка. 
 
- Исключения: 
  - Не импортируем DomainException и Throwable через use, используем полное имя: 
    - throw new \DomainException('Сообщение на русском языке'); 
  - Сообщения исключений пишем на русском и максимально конкретно.

## 8. Bitrix и Event‑слой 
 
- Bitrix‑код: 
  - Может находиться только в: 
    - Репозиториях (доступ к БД/инфоблокам/ORM), 
    - Event‑регистрации (`EventRegister/events.php`), 
    - Listener‑обработчиках (в минимальном объёме, обычно только получение данных события и вызов доменных Listener/Command). 
  - Любой Bitrix‑код в доменных сущностях, сервисах (за исключением явных инфраструктурных), Handler/Fetcher и HTTP‑Action запрещён. 
 
- Регистрация событий: 
  - Файл local/classes/Expoline/{Domain}/EventRegister/events.php. 
  - Подключается в bitrix/php_interface/init.php. 
  - Пример регистрации: 
    - EventManager::getInstance()->AddEventHandler("module", "Event", "\Path\To\Handler::handle"); 
 
- Listener: 
  - Расположение: local/classes/Expoline/{Domain}/Listener/{Logic}/Handler.php. 
  - Статический метод handle(): 
    - Оборачиваем в try-catch, если нужна итеративная обработка событий без падения всего процесса. 
    - Получаем из события только необходимые данные и передаём в команды/фетчеры отдельными параметрами, не передавая целый event‑объект. 
    - Пример: 
      - \Expoline\Container\Container::get(HandlerClass::class)->handle($param1, $param2); 
    - При ошибках — логируем через Logger::toFile(...), сообщение и трейс.

## 9. Конфигурация DI и конфиг‑файлы доменов 
 
- Расположение конфигов: api/v1/config/common/{domain}.php. 
- Именование: 
  - Имя файла — домен в kebab‑case (`billing.php`, devstatistic.php, auto-invoce.php и т.п.). 
 
- Структура конфига: 
  - Возвращаем массив: 
    - Ключи Class::class → static function (ContainerInterface $container): Class { ... }, 
    - Ключ config → массив доменных конфигов. 
  - Пример структуры: 
    - return [ 
    -     SomeClass::class => static function (ContainerInterface $container): SomeClass { ... }, 
    -     'config' => [ 
    -         'billing' => [ 
    -             'iblock_code' => 'billing', 
    -         ], 
    -     ], 
    - ]; 
 
- Получение iblockId: 
  - В конфиге домена: 
    - Получаем код инфоблока из 'config'. 
    - Инициализируем iblockId через (new \Expoline\Service\IBlockHelper())->getIBlockIdByCode($code);.

    - Передаём iblockId в конструктор репозитория. 
 
- DI‑определения: 
  - В конфиг‑файлах описываем: 
    - Репозитории, 
    - Доменные сервисы, 
    - Инфраструктурные классы (логгер, вспомогательные сервисы). 
  - Не описываем: 
    - Command/Query‑классы (команды и запросы) в `common`‑конфигурации DI — они загружаются автоматически через Slim по автозагрузке, 
    - Handler‑классы, 
    - Fetcher‑классы, 
    - Listener‑классы — они подхватываются через автозагрузку Slim.

## 10. Стиль кода и соглашения 
 
- Типизация: 
  - Включаем declare(strict_types=1);. 
  - Обязательно указываем типы параметров и возвращаемых значений во всех методах и функциях. 
  - Если метод обязан вернуть значение — указываем конкретный тип, не mixed. 
  - Если метод может ничего не вернуть — используем void или ?Тип. 
 
- Свойства и конструкторы: 
  - В доменных сервисах и Handler/Fetcher: 
    - Свойства объявляем в конструкторе как private readonly. 
  - В сущностях: 
    - Свойства публичные, не readonly. 
    - Имя идентификатора — id (строка, в нижнем регистре). 
 
- Именованные аргументы: 
  - Везде, где это возможно (особенно при создании сущностей и DTO), используем именованные аргументы: 
    - new Entity(id: '', name: $name, ...); 
    - Entity::buildNew(name: $name, companyId: $companyId, ...); 
 
- Исключения: 
  - Для бизнес‑ошибок используем \DomainException. 
  - Сообщения: 
    - Только на русском, понятные пользователю/разработчику. 
  - Не импортируем DomainException и Throwable в use: 
    - Пишем полное имя: \DomainException, \Throwable. 
 
- Логирование: 
  - Только через \Expoline\Service\Logger::toFile('домен/use-case', [...]);. 
  - Имя лога: 
    - В формате домен/use-case, части разделяем дефисами (например, `billing/create-key`). 
 
- Чистота кода: 
  - Неиспользуемые `use`‑импорты удаляем. 
  - Следим за форматированием (PSR‑12 плюс принятый стиль в проекте). 
  - Без глобальных переменных: 
    - Весь доступ к зависимостям — через DI. 
    - Исключение — старый Bitrix‑код в репозиториях при добавлении элементов (например, $GLOBALS['USER'] в `CIBlockElement::Add`).

## 11. Поток обработки HTTP‑запроса 
 
- Типичный сценарий: 
  1. Запрос POST /api/v1/method попадает в Slim. 
  2. Slim через конфиг slim.php и http.php находит соответствующий маршрут и Action. 
  3. Action: 
     - Парсит тело/параметры запроса. 
     - Создаёт Command/Query. 
     - Вызывает Handler/Fetcher. 
     - Преобразует результат (DTO/сущности) в простой массив. 
     - Возвращает JsonResponse с данными или ошибкой. 
  4. Внутри Handler/Fetcher: 
     - Вызываются репозитории и доменные сервисы. 
     - Репозитории обращаются к Bitrix ORM и/или старому ядру для записи. 
 
- DDD‑границы: 
  - HTTP‑слой ↔ Домены: только через Command/Query/Listener. 
  - Домены ↔ БД/Bitrix: только через репозитории и инфраструктурные сервисы.

## 12. Дополнительные требования и запреты 
 
- Запрещено: 
  - Размещать Bitrix‑код вне репозиториев и слоя интеграции с Bitrix (кроме регистрации событий и минимальной логики в Listener). 
  - Использовать try-catch в репозиториях. 
  - Делать проверки на пустоту/валидацию в Entity::buildNew и buildFromData (кроме технического преобразования типов). 
  - Делать проверки на подключение модулей Bitrix в репозиториях. 
  - Передавать внутрь домена целиком объекты событий Bitrix — только извлечённые данные. 
  - Создавать геттеры/сеттеры в сущностях без острой необходимости. 
 
- Обязательно: 
  - Следовать структуре каталогов и неймингу, как в существующем модуле Billing. 
  - Для новых доменов повторять архитектуру: 
    - Entity, Repository, Command, Query, Service, EventRegister, Listener, Http/Action. 
  - В конфиг‑файлах использовать замыкания с ContainerInterface и именованные параметры при создании объектов.

## 13. Верстка и представления 
 
- В рамках DDD‑концепции PHP‑проекта: 
  - Вся верстка (шаблоны Bitrix, компоненты, JS‑файлы) располагается вне доменного слоя: 
    - В компонентах Bitrix (`local/components/...`), 
    - В шаблонах компонентов,
